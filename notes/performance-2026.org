#+TITLE: vcsh performance review (2026-10-01)

Review of interpreter performance at commit c7a22fa, with candidate
improvements for future work. Tracked in TODO.org under "Performance".

* Environment and method
- arm64 Linux VM, gcc 11, RELEASE build (-O3). Default DEBUG build (-O) is
  only 15-20% slower, so build type isn't the bottleneck.
- Build needed local fixes: drop -m64 from config.unix, replace int3 with
  __builtin_trap() in unix-sys.c, touch vm/TAGS (no etags).
- Profile from a PROFILE=on (gprof) build; perf unavailable. Proportions are
  fine; call counts for inlined evaluator functions are not reliable.
- Micro-benchmarks are at the end of this file. Compare against CPython 3.10
  on the same machine.

gprof: ~60% execute_fast_op, ~15% GC (mark + sweep), ~6% lcons.
fib30 + loop10M: ~48M lcons calls, 51 GCs, heap 1M cells x 32 bytes.

* Where the time goes
1. Every operand is a full recursive execute_fast_op call: stack check,
   interrupt poll, 3-word eval frame push, and argv[ARG_BUF_LEN] (64 slots,
   512 bytes) of C stack. Fetching a literal or local costs a full eval.
2. Every closure call allocates: arg_list_from_buffer conses the args, then
   extend_env conses a frame. About 3-4 cells per call, which drives the GCs.
3. Local lookup is O(depth): lenvlookup_by_index walks frame lists, then
   argument lists.
4. Only car, cdr, not, null?, eq? are integrated as fast-ops. +, -, <, =
   are full subr calls with common_number_type dispatch, even for fixnums.
5. Each :optional expands to three nested closure creations and calls;
   :keyword is much worse.
6. Generic functions re-dispatch on every call: (map type-of args), cons a
   (gf . signature) key, cache hash lookup, then call-next-method via closure.

* Candidate improvements (rough order of payoff for the effort)
** 1. Evaluate trivial operands inline [prototyped, patch below]
   In the FOP_APPLY / FOP_APPLY_GLOBAL arg loops, a literal, local ref, or
   bound global ref with no `next` is handled directly instead of recursing.
   Measured: fib30 0.198 -> 0.160 s, loop10M 0.88 -> 0.69 s,
   plain call 146 -> 115 ns. Full test suite passes (7364 checks).
   No scc0 or image changes needed. Same idea applies to `if` conditions.
** 2. Integrate fixnum arithmetic/comparison as fast-ops
   FOP_ADD2, FOP_SUB2, FOP_LT2, FOP_NUMEQ2: inline when both args are
   fixnums, otherwise fall back to the subr. Needs new opcodes in
   scan-constants.i, evaluator cases, define-integration entries, and an
   scc0 refresh. Likely a large win on numeric loops.
** 3. Vector environment frames
   Allocate one frame object holding the argument values. Drops
   arg_list_from_buffer, makes lookup a frame walk plus array index, and
   roughly halves allocation per call. Watch out: rest args and
   the-environment depend on the list layout. Overlaps with "move argument
   buffers onto the Lisp stack".
** 4. Reduce GC cost
   Cheap: bigger default heap segment, or growth based on how much survives
   a collection. Longer term: lazy sweeping, fewer boxed flonums.
** 5. Lambda lists in the VM
   Parse :optional/:keyword in one step at the closure boundary instead of
   nested closures. Would bring :keyword from ~1 us down near a plain call.
** 6. Generic-function dispatch
   Cache per generic function on the type of the first argument, without
   consing a key; use the full signature only for multi-arg dispatch. Skip
   call-next-method machinery for single-method gfs.
** 7. Linear bytecode compiler (already in backlog)
   Removes the recursion in (1) and node pointer-chasing altogether.
   (1)-(3) pay off either way and are prerequisites in spirit.
