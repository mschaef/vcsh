#+TITLE: vcsh bootstrap (scc0) analysis (2026-10-01)

Analysis of how the self-hosting build works, where it is brittle, and
what could make it more predictable. Tracked in TODO.org under
"Bootstrap".

* How the bootstrap works today
1. vm/scansh0 (the *new* VM) loads scc0/scheme.scf and
   scc0/compiler-run.scf (the *old* image and compiler).
2. setup-image-compile.scm renames every package except system and
   keyword to host-*, creates empty target packages, re-homes the host
   symbols into the target packages, copies host global values into new
   target symbols, and imports a hand-picked list
   (*shared-target-symbols*) into the target.
3. The old compiler compiles scheme.scm into scheme.scf, which is linked
   into vcsh0. vcsh0 compiles the library modules; vcsh is built from that.

Consequence: the shipped image is always compiled by scc0's compiler,
never by the compiler in the current source. Compiler changes only reach
the image after 'make update' in scc0/ and a rebuild. 343 of 1,948
commits touch scc0/scheme.scf.

Update (2026-10-02, branch bootstrap-predictability): improvements 1-3
below are done. The image is now compiled twice: stage 1 by scc0 (into
scheme-core/build/stage1/), stage 2 by the stage 1 image (scheme.scf and
compiler-run.scf), and stage 2 is what's linked, so the shipped image is
compiled by the current compiler.

* Assessment 1: VM changes must be made in steps (confirmed)
scc0 runs on the new VM, so everything the old image depends on is an
interface the VM can't break until scc0 is refreshed:
- Fast-op opcodes and semantics. Baked into scc0's compiled code, which
  the new VM must run. The old compiler also bakes its own opcode numbers
  into its output (#.system::FOP_* in compiler-fasm.scm was evaluated
  when scc0 was built), so the new image is written with the *old*
  opcode numbers.
- FASL format. No version header, so a mismatch fails partway through a
  load.
- Subr (built-in C function) names. FASL stores them by name and the
  loader looks them up, so removing or renaming one breaks loading scc0.
- Trap numbers, typecodes, VM control fields. Baked in with #. reads.
- Values the old image's code checks at run time. Example (2026-10-02):
  system-info :platform-name changed from :linux to :macos on macOS in
  the same commit that removed platform-case from scheme-core. The old
  scc0 image still ran its own platform-case on the host side, which
  errors on any platform but :win32 and :linux, so the build broke on
  macOS. It passed on Linux, where the value didn't change. Fixed by
  refreshing scc0 (branch refresh-scc0). Test VM changes that alter
  observable values on every platform, or simulate the other one.

Adding a fast-op is two steps: change VM and compiler, build, 'make
update', build again. Renumbering or removing one needs the VM to support
both versions in between. Performance items 2 and 3
(notes/performance-2026.org) hit this directly.

* Assessment 2: the compiler overwrites itself (confirmed)
1. Every definition is executed in the compiling process.
   compile-toplevel-definition (compiler-file.scm) calls %define-global
   on each value it compiles. Needed so target macros can call target
   functions, but it means the image is loaded into the compiler as it is
   compiled.
2. *shared-target-symbols* includes ordinary functions: member, not, <,
   <=, >, >=, =, eq?, equal?. list.scm defines member, so from then on the
   host compiler uses the target's member. Verified: a file that defines
   member (via %define/%lambda) to call an unbound function, followed by
   an eval-when, fails inside that function, because the host's eval-when
   handler calls member. The others are rebound to subrs, which is
   harmless unless those subrs change.
3. The whole system package is shared. scan-constants.scm redefines
   system::FASL_OP_*, TRAP_*, etc. at compile time. Host code that reads
   them at runtime (fast-write.scm's FASL writer, compiler-file.scm's
   FASL_OP_LOADER_DEFINEA0, ...) switches to the new values mid-compile.
   FASL output written before the include uses old numbers, everything
   after uses new ones. Fast-op numbers stay old (see above).
   system::LOAD-TIME-GET-PACKAGE / SET-PACKAGE! are also redefined.
4. VM-global state has no namespace. error-handling.scm, number.scm,
   memory.scm and main.scm install trap handlers in
   eval-when (:compile-toplevel ...), so partway through the build the
   host's handlers for errors, fixnum overflow, GC growth and RUN0 are
   replaced by the target's. Handler frames (FOP_GET/SET_HFRAMES),
   *package-list* and *provided-packages* are shared too. Changing the
   handler-frame representation in error-handling.scm means the old
   compiler's handler-bind runs through the new signal code.

Debugging trap: because host symbols are re-homed, they print with
target package names.

* Other predictability issues
- [fixed] scheme.scf had no prerequisites, so editing a scheme-core source
  didn't rebuild the image until 'make clean-scheme'.
- [fixed] 'make update' in scc0/ copied a new 500 KB image without
  checking it.
- [fixed] Builds weren't reproducible: #.(current-date) in scheme.scm meant
  two builds of the same source differed. Apart from the date, compiles
  were already deterministic (checked byte for byte).
- scc0/scc0 and scc0-good wrapper scripts are stale (already in TODO).
- [fixed] scansh0 treated arguments starting with "/" as options (Windows
  style). Fixed in main.scm, and the refreshed scc0 (9c6fff1) has it.
- [fixed] The scheme-core Makefile passed --initial-package:scheme to the
  compiler, an option removed long ago; every build printed "Unknown
  command line argument: initial-package". Dropped (it was ignored).

* Improvements, roughly in order
** Predictability (cheap)
1. [done] Real dependencies for scheme.scf: all scheme-core/*.scm,
   vm/scan-constants.scm, scansh0 and the scc0 images. A wildcard is
   fine to start with.
   As built: each stage depends on scheme.scm, setup-image-compile.scm,
   the files scheme.scm includes (taken from its include forms, so test
   files don't trigger a rebuild), scansh0 and the previous stage's
   images. compiler-run.scf depends on compiler-run.scm, scansh0 and the
   previous stage's images.
2. [done, with a change] FASL header with a format version and a hash of
   scan-constants.i plus the subr table (names and arity). The loader
   rejects a mismatch with a clear message.
   As built: compiled files start with "#vcsh-fasl <version> <hash>". '#'
   is a FASL comment opcode, so older readers skip the line. The hash
   (vm_abi_hash, core.c) covers every scan-constants.i table, name and
   value, plus every subr's name and arity; system-info :vm-abi-hash
   shows it. A different format version is an error. A different hash is
   only a warning naming the file: scc0 has to keep loading on newer VMs
   until it's refreshed (Assessment 1), and most interface changes are
   additions it can live with, so rejecting it would break the
   bootstrap. Once scc0 carries a header (after the next 'make update'),
   every build after a VM interface change warns that scc0 is stale.
   scc0 images made before this change have no header and aren't
   checked.
3. [done] Automate the second stage. Stage 1: scc0 compiles the image.
   Stage 2: vcsh0 compiles it again, and that is shipped, so compiler
   changes take effect in one build. 'make bootstrap-check' confirms
   stage 3 is byte-identical to stage 2, and 'make update' copies only a
   checked image. Needs the build date injectable (e.g. from the
   environment) for reproducible output.
   As built: stage 2 runs scansh0 with the stage 1 .scf files rather than
   vcsh0 (same thing, without linking). 'make bootstrap-check' (top level
   or scheme-core/) builds stage 3 in build/stage3/ and compares with
   cmp; 'make update' in scc0/ runs it first. The build date comes from
   SOURCE_DATE_EPOCH (the reproducible-builds.org convention), which the
   makefile sets to the time of the last commit touching the image
   sources; outside a git checkout it falls back to the current time, so
   bootstrap-check then needs SOURCE_DATE_EPOCH set explicitly. The
   images depend on the value through a stamp file
   (build/source-date-epoch). Without that, the first version failed
   bootstrap-check after a commit: stage 2, built before the commit, kept
   the old date while stage 3 got the new one. Cost: about 6 s more per image
   rebuild (debug build), for the second compile.
** Less crosstalk (moderate)
4. Trim *shared-target-symbols* to syntax keywords and type names. member
   and the comparison functions are probably there for macro expansions
   that compare symbols; needs checking, but sharing the symbol shouldn't
   be the fix.
5. Stop installing trap handlers at compile time: make those eval-whens
   :load-toplevel only, or have %set-trap-handler! refuse while an image
   compile is running.
6. [done] Make the host compiler independent of system:: values at
   runtime: the FASL writer should use constants fixed when it was built
   (as the fast-op table does), so redefinitions can't switch its output
   midway.
   As built: every FASL_OP_* reference in fast-write.scm, fasl-stream.scm
   and compiler-file.scm is now #.system::FASL_OP_*, read when that code
   is compiled. Each stage's writer uses the numbering current when it
   was compiled, which during an image compile is the target's (the
   include of scan-constants.scm comes before those files). A test in
   test-fast-io redefines system::FASL_OP_STRING and checks that FASL
   output still round-trips; it fails on the old writer.
   Extended to the rest of scheme-core: every value reference to a
   system::TRAP_*, VMCTRL_* or FOFS_* constant (50 of them, in
   error-handling.scm, io.scm, main.scm, memory.scm, number.scm,
   scheme.scm and tools.scm) is now #.-read as well, so no scheme-core
   code reads a system:: constant at run time. (Quoted symbols such as
   'system::FRAME_SUBR, used as frame-type tags, are unchanged.) A test
   in test-io swaps the VMCTRL input and output port variables and
   checks the current-port accessors are unaffected; it fails on the old
   io.scm.
   Trade-off: an image now always uses the numbering it was compiled
   with. That's right for every image running on the VM it was built
   for. For scc0 on a newer VM with renumbered constants, it is
   consistently wrong rather than wrong until the include switches it
   (which only worked by accident, via crosstalk). Fixing that properly
   is item 7, and the FASL header warning now flags a stale scc0.
   Left as is on purpose: the LOAD-TIME-GET-PACKAGE / SET-PACKAGE!
   closures that compiler-file.scm writes into each load unit. The host
   writes the target's versions once the target redefines them, but
   that's the right code for the image being built. They live in
   system:: because the system package exists before any image is
   loaded, and the closures appear at the start of scheme.scf.
** Structural (larger)
7. Pin scc0 to its own VM: treat scc0 as a git revision (old VM + old
   image) and build that VM in a worktree during bootstrap. The new VM
   then only has to read the old compiler's output, not run old code.
   Combined with 6, and taking opcode numbers from the target's
   scan-constants, VM changes become one-step edits.
8. Evaluate fewer definitions at compile time, Common Lisp style: only
   eval-when and macro definitions run in the compiler, with helpers that
   macros need wrapped explicitly. Removes crosstalk route 1 almost
   entirely, but touches a lot of scheme-core.

Relevance to a possible Rust VM (notes/history-and-direction.org): a
port has to read the same images and honour the same opcode, trap and
type-code numbering. Making that contract explicit and versioned (2) and
decoupling scc0 from the current VM (7) are what would let a second VM be
built and tested against existing images.

Suggested order: 1-3 first (they make every later change safer to test),
then 4-5. Do 6-7 before performance work that adds fast-ops.

* Reproducing the member crosstalk test
From scheme-core/ after a build (input path must be relative):
#+begin_src scheme
;; xtalk.scm
(%define member (%lambda () args (system::%panic "TARGET member called by host compiler")))
(eval-when (:load-toplevel) 1)
#+end_src
#+begin_src sh
../vm/scansh0 -Xinit-load=../scc0/scheme.scf -Xinit-load=../scc0/compiler-run.scf \
    --load-file:setup-image-compile.scm --output:xtalk.scf xtalk.scm
#+end_src
Fails with "unbound global: system::%panic", raised from inside the
target's member when the host compiler's eval-when handler calls it.
