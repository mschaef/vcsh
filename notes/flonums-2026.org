#+TITLE: Boxed flonums: impact and options (2026-10-01)

Assessment of vcsh's boxed flonum representation, with options to
remove or reduce the cost. Companion to notes/performance-2026.org.
No code changed yet.

* Current representation
- An lref_t is a pointer or an immediate with a 2-bit low tag:
  00 = heap ref, 01 = fixnum (62 bits), 11 = special (second-stage tag
  for bool/char/eof/unbound). Tag 10 is unused.
- Every flonum is a heap cell (TC_FLONUM): 8-byte header,
  double data, lref_t im_part. All cells are sizeof(lobject_t) = 32
  bytes, so a double costs 32 bytes, 4x its payload.
- A complex number is a flonum whose im_part points at a second flonum:
  2 cells, 64 bytes, and every real flonum op checks im_part.
- A vector of N doubles is N lref_t slots plus N cells: 40 bytes per
  element vs 8 unboxed.
- Every arithmetic result is a fresh cell (flocons -> new_cell). There
  is no flonum fast path: +, -, *, / are SUBR_2N calls that test
  FLONUMP, call get_c_complex on both args, then allocate.
- The GC is conservative (scans the C stack and registers) and
  non-moving, mark-and-sweep over fixed 1M-cell segments. Copying or
  generational schemes are therefore hard; options below avoid them.

* Measurements
arm64 Linux VM, gcc 11, DEBUG build, commit de2aad6. Times from
%time-apply0 (total, GC, cells allocated). Fixnum versions of the same
loops stand in for "unboxed floats": same evaluator work, no allocation.

| Benchmark (2M iterations)    | Total   | GC      | Cells/iter |
|------------------------------+---------+---------+------------|
| fixnum (+ acc 1)             | 0.338 s | 0.044 s |          4 |
| flonum (+ acc 1.0)           | 0.366 s | 0.055 s |          5 |
| fixnum (+ (* acc 0) 1)       | 0.392 s | 0.044 s |          4 |
| flonum (+ (* acc 0.5) 1.5)   | 0.447 s | 0.066 s |          6 |

| Benchmark (1M elements)      | Total   | GC      | Cells     |
|------------------------------+---------+---------+-----------|
| sum fixnum vector            | 0.238 s | 0.000 s | 16K       |
| sum flonum vector            | 0.258 s | 0.006 s | 1.0M      |

- Each boxed result costs about 14-20 ns (about 5.5 ns of that is GC,
  the rest is allocation and type dispatch).
- Today that is only 8-14% of a float-heavy loop, because the evaluator
  itself allocates ~4 cells per closure call (arg list + env frame) and
  costs ~170 ns per iteration. Boxing is hidden behind evaluator
  overhead.
- Memory is the more visible cost now: filling a 600K-element vector
  with flonums grew the heap by a full segment (+32 MB); the same
  vector of fixnums needed no growth.

** Why this gets worse
The planned evaluator work (performance-2026.org items 1-3: inline
operands, fixnum fast-ops, vector frames) roughly halves per-call
allocation and per-call time, and fast-ops will only help fixnums.
After that, boxing is plausibly 25-35% of a float loop, and float code
falls further behind equivalent fixnum code. It makes sense to settle
the representation before or alongside that work, and before any Rust
port.

* Options
** A. Immediate flonums in the unused 10 tag (prototyped)
Ruby's "flonum" encoding (since 1.9/2.0) fits vcsh's tag layout:
fixnum = 01, flonum = 10, same 2-bit mask.
- Encode: if bits 62..60 of the double are 011 or 100 (magnitude in
  [2^-255, 2^257), about 1.7e-77 to 2.3e77), rotate the 64 bits left
  by 3, clear bit 0, set bit 1. +0.0 gets a reserved encoding, so +2^-255
  (which would collide with it) is boxed. Everything else (-0.0, tiny,
  huge, inf, NaN) stays boxed as today.
- Decode: rotate right by 3 after restoring the dropped exponent bit
  from bit 63. A handful of ALU ops, lossless, full double precision.
- Nearly all values in real workloads are immediate: no allocation, no
  GC, 8 bytes in a vector slot.
- Fits the existing VM:
  - NIL stays 0, fixnums stay 62 bits, lref_t stays a pointer type.
  - The conservative GC rejects tag-10 words already (not cell-aligned),
    and LREF_IMMEDIATE_P is true, so gc_mark skips them.
- Work: FLONUMP becomes "immediate or boxed"; FLONM decodes; flocons
  encodes or falls back; TYPE() learns the new tag. About 40 FLONM/
  FLONUMP sites in vm/, plus sxhash, equalp, the FASL writer,
  debug-printer and %typecode (class-graph.scm maps typecodes to class
  names, so immediates need a typecode that maps to 'flonum).
- Semantics: eq? becomes true for some equal floats and not others.
  R5RS leaves eq? on numbers unspecified, but check that scheme-core
  doesn't rely on flonums being distinct objects.
- Needs B first, since an immediate has no room for im_part.
- Prototyped on branch immediate-flonums, which builds on complex-type;
  see "Prototype of option A" below.

** B. Give complex numbers their own type (prototyped)
New TC_COMPLEX cell holding two inline doubles; TC_FLONUM holds only a
double. Complex drops from 2 cells to 1, and real arithmetic no longer
checks im_part. Useful on its own and a prerequisite for A. Done on
branch complex-type; details under "Prototype of option B" below.

** C. Fused float fast-ops in the compiler
Have the compiler recognise nested arithmetic, e.g.
(+ (* zr zr) (* zi zi)), and emit one fast-op that evaluates the tree in
C doubles, boxing only the result. It falls back to the generic subrs
when an argument isn't a flonum.
- Removes intermediate allocations and, more importantly, most of the
  evaluator round trips. It pays off with or without A.
- Natural extension of performance item 2 (FOP_ADD2 etc.); needs new
  opcodes and an scc0 refresh.

** D. Homogeneous float vectors
An f64vector type (SRFI-4 style) storing raw doubles in a gc_malloc'd
block, like strings.
- Bulk float data drops from 40 to 8 bytes per element, and the GC no
  longer marks per-element cells.
- Reads still produce a flonum (immediate under A). Worth doing if
  numeric arrays matter, e.g. for a future vCalc.
- Additive and low risk.

** E. Cheap mitigations
- Inline the flocons allocation fast path (pop the freelist directly).
- Add a FLONUMP fast path at the top of ladd/lsubtract/lmultiply
  before get_c_complex (with B, FLONUMP already excludes complex).
- Grow the heap based on survival rate (performance item 4).
- Together these might recover a third of the per-box cost. They don't
  change memory use.

** F. NaN-boxing (not recommended here)
Store every value as a double and put pointers, fixnums and specials in
NaN payloads.
- Floats are fully unboxed.
- Costs:
  - NIL == 0 is +0.0, so NIL has to move, and NULLP/zero-initialisation
    assumptions run through the VM.
  - Fixnums shrink to at most 51 bits.
  - lref_t stops being a dereferenceable pointer, which changes every
    x->as.* access.
  - The conservative stack scan has to decode every word.
- A large rewrite for little gain over A. Worth considering only for a
  from-scratch Rust VM.

* Prototype of option B (branch complex-type, 2026-10-01)
** What changed
- New typecode TC_COMPLEX (24; numbers 14/19/21 left as gaps because
  scc0 may still map them). Cell holds two inline doubles; TC_FLONUM
  holds only a double, and GC no longer traces flonums.
- Predicates: FLONUMP is a real flonum only; COMPLEXP is TC_COMPLEX;
  REALP = fixnum or flonum; new INEXACTP = flonum or complex;
  NUMBERP includes complex. FLOIM is gone; CMPLXRE/CMPLXIM read the
  cell directly.
- class-graph.scm maps TC_COMPLEX to 'complex directly, so
  %representation-of no longer special-cases flonums.
- Class graph flipped: flonum < complex < number (was complex < flonum
  < number). Methods on complex now apply to flonums, and flonum methods
  no longer apply to complex numbers. The generic-function dispatch
  tests were updated to match, and test-class-graph checks the new
  relationships.
- Behavior changes, all deliberate:
  - (- c d) on complex numbers was missing a return and fell into the
    fixnum path, returning garbage. Fixed.
  - exp of a complex used to return re*(cos im + i sin im), which is
    wrong. It now raises "unimplemented", like sin, cos and sqrt.
  - Class-graph dispatch, as above.
  Otherwise, a 40-case probe of complex operations gave identical output
  before and after.
- Builds with the existing scc0 image; no 'make update' needed.
- Tests: 7399 checks pass, including new complex-arithmetic and
  class-graph tests.

** Measurements (same harness as above, 2M iterations)
| Loop                 | before            | after             |
|----------------------+-------------------+-------------------|
| (+ acc 0+1i)         | 0.378 s, 6 c/iter | 0.358 s, 5 c/iter |
| (+ (* acc 0.5) 0+1i) | 0.477 s, 8 c/iter | 0.439 s, 6 c/iter |
| real flonum loops    | 0.362 / 0.442 s   | 0.360 / 0.438 s   |
100K live complex numbers: 200K cells before, 100K after. Complex
arithmetic now costs the same as real flonum arithmetic; real flonum
code is unchanged, as expected.

* Prototype of option A (branch immediate-flonums, 2026-10-02)
** What changed
- Smaller than estimated: everything goes through FLONUMP, FLONM and
  flocons, so only those and TYPE() needed to change.
  - scan-types.h: LREF1_FLONUM = 0x2; FLONUM_IMMEDIATE (encode, returns
    false when the value must be boxed) and FLONUM_IMMEDIATE_VALUE
    (decode); TYPE() maps the tag to TC_FLONUM; FLONUMP accepts either
    form; FLONM decodes immediates.
  - number.c: flocons returns an immediate when it can. ladd,
    lsubtract and lmultiply check for two fixnums first, before any
    other type tests (see Measurements).
  - vm-tests.c: bit-exact round-trip tests through flocons/FLONM for
    boundary values (both ends of the range, the +2^-255 collision,
    -0.0, denormals, DBL_MAX, infinities, NaN payloads), every exponent
    with several mantissas, and 2M pseudo-random bit patterns.
- Nothing else needed changing: the GC skips immediates, sxhash goes
  through FLONM, %typecode goes through TYPE(), and FASL writes values.
  Builds with the existing scc0 image.
- Tests: 7399 Scheme checks and the VM tests pass, DEBUG and CHECKED.

** Behavior changes
- eq? is now #t for equal immediate flonums, e.g. (eq? 1.5 (+ 1.0
  0.5)), and still #f for equal boxed ones (-0.0, 1e300, NaN). eqv?,
  equal? and = are unchanged. An identity hash table now finds an
  immediate flonum key by value. No test or library code relied on the
  old behavior.
- %immediate? is #t for immediate flonums, so the printer and
  fast-write treat them as unshared, as they do fixnums.
- %obaddr of an immediate flonum returns a meaningless number (the
  encoding doesn't fit in a fixnum). Only the printer uses %obaddr, for
  unprintable objects, so this doesn't show up.

** Measurements
RELEASE build (-O3), before = complex-type, after = immediate-flonums
with the fixnum-first check. Best of 6 interleaved runs (the VM is
noisy; medians agree except where noted):
| Benchmark            | before  | after   | change |
|----------------------+---------+---------+--------|
| fixnum (+ acc 1)     | 0.282 s | 0.282 s | 0%     |
| flonum (+ acc 1.0)   | 0.301 s | 0.292 s | -3%    |
| fixnum *+ loop       | 0.331 s | 0.328 s | -1% (a) |
| flonum *+ loop       | 0.368 s | 0.345 s | -6%    |
| mandelbrot 200x200   | 0.409 s | 0.368 s | -10%   |
(a) Medians were 0.334 vs 0.351 s (+5%), but runs on both sides ranged
    from about 0.33 to 0.37 s, so this one needs a quieter machine to
    settle.

DEBUG build, cells allocated:
| Benchmark                  | before | after |
|----------------------------+--------+-------|
| flonum (+ acc 1.0), 2M     | 10.0M  | 8.0M  |
| flonum *+ loop, 2M         | 12.0M  | 8.0M  |
| mandelbrot 200x200         | 11.4M  | 4.1M  |
| sum a 1000-float vector 1K | 1.0M   | 16K   |
| fill 600K-float vector     | 600K   | 13    |
- Float loops now allocate exactly as much as the fixnum versions (all
  remaining allocation is the evaluator's argument lists and frames),
  and run within 2-4% of them. Mandelbrot GC time halved.
- Filling a 600K-element vector with floats no longer grows the heap
  (1 segment instead of 2).
- Without the fixnum-first check, fixnum loops were 1-2% slower (0.287
  -> 0.290 s and 0.334 -> 0.340 s, median of 3), because the arithmetic
  subrs tested INEXACTP before the fixnum path and FLONUMP now checks
  the tag before the cell type. With the check, fixnum loops are back
  to where they were. The comparison functions (=, <, ...) still go
  through common_number_type; the planned fixnum fast-ops would cover
  them.
- As the evaluator gets faster (performance-2026.org items 1-3), boxing
  would have become a larger share of float code, so the relative
  benefit of A grows.

* Future work and open decisions
** Decisions
- Merge complex-type to master, or revise first. Then
  immediate-flonums, which builds on it.
- Where fixnum sits in the class graph. It is directly under number, so
  a method on complex doesn't apply to fixnums even though every fixnum
  is a complex number. Options: put fixnum under complex, or add a
  'real class (fixnum, flonum < real < complex < number).
- What complex? should mean. It returns #f for reals and fixnums
  (complex? 1.5 => #f); R5RS says every number is complex. Tied to the
  class-graph question above.
- How to compare complex numbers. = should compare both parts; <, >,
  <=, >= should probably raise wrong-type for a non-real argument.
- Whether get_c_flonum should raise on a complex argument instead of
  returning the real part (see the REVISIT list below).
- Option A:
  - Whether the eq? change is acceptable: equal immediate flonums are
    eq?, equal boxed ones (-0.0, out-of-range, NaN) are not.
  - Whether -0.0 should get a reserved immediate encoding like +0.0, so
    that all common values avoid allocation.
  - %obaddr on immediates: leave, return #f, or return the raw bits.
- Which of options C, D and E to pursue, and when (see "Suggested
  order").

** Complex arithmetic still to finish (some marked REVISIT in vm/)
- = and < compare only real parts: (= 1+2i 1+5i) is #t, and < accepts
  complex arguments (common_number_type).
- get_c_flonum silently returns the real part of a complex, so floor,
  ceiling, round, truncate, inexact->exact and number->string drop the
  imaginary part.
- exp, sin, cos, tan, asin, acos, atan, sqrt and expt raise
  "unimplemented" for complex arguments. lsqrt already contains
  unreachable code for the complex case.
- string->number doesn't parse "1+2i", though the reader does.
- langle has an unused complex_x variable (compiler warning).

** Housekeeping
- Refresh scc0 ('make update') after merging. Until then the host image
  maps complex values to type #f, which only matters if the build ever
  compiles a complex literal into the image.
- The CHECKED build overflows the stack in test-symbols, on master too.
  The suite passes with (%set-stack-limit #f). Not flonum-related;
  also in TODO.org.

* Suggested order
1. B (complex as its own type): prototyped; merge once reviewed.
2. A (immediate flonums): prototyped; removes nearly all flonum
   allocation. Merge after B.
3. C, together with the fixnum fast-ops / bytecode work.
4. D if bulk numeric data becomes a real use case. E as filler.

* Side finding (fixed)
sxhash hashed a flonum as get_c_fixnum(obj), i.e. its truncated integer
value, so every flonum in [0, 1) hashed to 0. It now hashes the mixed
bit pattern, with -0.0/0.0 and all NaNs normalized to match equal?
(sxhash_flonum in vm/hash-table.c). With option A, immediate flonums
still hash through sxhash_flonum, so equal? keys hash the same whether
boxed or immediate.

* Benchmark source
Run with: echo ':X' | scheme-core/vcsh flonum-bench.scm
#+begin_src scheme
(define (bench name thunk)
  (gc)
  (let ((r (scheme::%time-apply0 thunk)))
    (format #t "~a: total ~a s, gc ~a s, cells ~a\n"
            name (vector-ref r 1) (vector-ref r 2) (vector-ref r 3))))
(define (fixloop n acc) (if (= n 0) acc (fixloop (- n 1) (+ acc 1))))
(define (floloop n acc) (if (= n 0) acc (floloop (- n 1) (+ acc 1.0))))
(define (fixmul n acc) (if (= n 0) acc (fixmul (- n 1) (+ (* acc 0) 1))))
(define (flomul n acc) (if (= n 0) acc (flomul (- n 1) (+ (* acc 0.5) 1.5))))
(bench "fix + loop 2M " (lambda () (fixloop 2000000 0)))
(bench "flo + loop 2M " (lambda () (floloop 2000000 0.0)))
(bench "fix *+ loop 2M" (lambda () (fixmul 2000000 0)))
(bench "flo *+ loop 2M" (lambda () (flomul 2000000 0.0)))
(define v (make-vector 1000 1.5))
(bench "flo vsum 1M" (lambda () (dotimes (j 1000) (let ((s 0.0)) (dotimes (i 1000) (set! s (+ s (vector-ref v i))))))))
(define vi (make-vector 1000 1))
(bench "fix vsum 1M" (lambda () (dotimes (j 1000) (let ((s 0)) (dotimes (i 1000) (set! s (+ s (vector-ref vi i))))))))
#+end_src
