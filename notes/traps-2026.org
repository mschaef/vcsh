#+TITLE: vcsh trap handlers (2026-10-01)

Inventory of VM traps and the handlers installed for them, as of the
structure cleanup (traps 2 and 7 removed). Written up ahead of reworking
traps; no decisions made yet. Tracked in TODO.org under "Traps".

* Mechanism
- The VM raises a trap with vmtrap(trap, options, argc, ...)
  (vm/evaluator.c). The handler is a Scheme procedure stored in
  interp.trap_handlers[] (sized TRAP_LAST + 1).
- Handlers are called as (handler trapno frame . trap-specific-args).
- Options:
  - VMT_MANDATORY_TRAP: no handler installed means a VM panic.
  - VMT_OPTIONAL_TRAP: no handler means the trap is skipped.
  - VMT_HANDLER_MUST_ESCAPE: the handler must leave via throw/catch;
    returning normally panics.
- The VM installs no handlers itself. scheme-core installs them all
  with %set-trap-handler!, inside
  (eval-when (:compile-toplevel :load-toplevel :execute) ...).
- %trap-handler reads a handler back. To list them all:
  #+begin_src scheme
  (dotimes (i 28)
    (format #t "~a ~a\n" i (scheme::%trap-handler i)))
  #+end_src

- trap-global-define-handler runs *global-define-hook*.
- trap-user-break signals 'user-break (catchable via 'ignore-user-break).
- trap-uncaught-throw aborts with 'scheme::uncaught-throw.
- trap-signal just does (abort tag retval).

* Observations
- History: some of these traps and handlers came about for vCalc, the
  Windows calculator that hosted an earlier vcsh (see
  notes/history-and-direction.org). Which ones isn't recorded; interrupt
  handling (USER_BREAK, TIMER_EVENT) is a likely candidate. Worth
  considering when deciding what to keep for a future macOS host.
- Dead traps: 0, 4, 6, plus 3 (SIGNAL has a handler but the VM never
  raises it, so trap-signal is unreachable this way). These could be
  removed like the structure traps, leaving numbered gaps.
- Trap 4 is a latent hazard: interrupts are raised as mandatory traps, so
  if anything ever set VMINTR_TIMER the VM would panic for lack of a
  handler.
- Bootstrap crosstalk: every %set-trap-handler! call is inside
  eval-when (:compile-toplevel ...), so during an image build the
  target's handlers replace the compiler's own mid-compile. See
  notes/bootstrap-2026.org, crosstalk route 4.
- Handlers are spread across four files (error-handling.scm, number.scm,
  memory.scm, main.scm) plus tools.scm, with no single place that shows
  the full table.
- The eight fixnum overflow traps share one handler and one generic
  message; whether they need separate trap numbers is an open question,
  as is promoting to flonum (or bignums) instead of erroring.
- vm/main.c init_base_scheme_objects clears handlers with
  "ii < TRAP_LAST", so the last slot isn't explicitly reset (harmless,
  since interp is zero-initialized, but off by one).

* Open questions (undecided)
- Which dead traps to remove, and whether to keep 3/4 for planned use.
- Whether trap installation should move out of :compile-toplevel.
- Whether to centralize the handler table in one file.
- Whether overflow should error or promote.
